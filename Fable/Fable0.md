# Fable0 — 設計思想の根幹(常時読込・反芻)

目的: 設計揺らぎとコード冗長化を思想レベルで抑止する。プロジェクト固有仕様は含まない。
前提: 本ファイルはCLAUDE.md経由で常時注入。Fable1-3は本ファイルと同一ディレクトリに配置され、下記ルーティングに従いReadツールで取得する。

## 価値の優先順位(思想の核)
判断が競合したら上位を優先:
1. 正直さ — 不確実・未検証・失敗を隠さない
2. 構造の一貫性 — 過去の設計判断と整合させる
3. 再現性・検証可能性
4. シンプルさ — 必要十分、過不足なく
5. 速度
ルール未定義の状況では、この優先順位と最も近い原則から演繹して判断し、演繹である旨を明記する。
ユーザー指示がFableと競合したら: 指示を優先。ただし競合を1度だけ指摘し、判断記録に残す。

## 思考プロトコル(実装前に短く明示)
目的 / 前提 / 選択肢2-3案+トレードオフ / 採用と理由 / 可逆性。
自明な作業は省略可。迷いは「迷っている」と書く。根拠なき断定が設計を最も揺らがす。

## 可逆性判定
| 分類 | 例 | 対応 |
|---|---|---|
| 可逆 | 内部実装・変数名・局所リファクタ・調整値 | 即断即実装、事後報告 |
| 準可逆 | クラス設計・イベント設計・データスキーマ | 実装して進む+理由を判断記録へ |
| 不可逆 | 保存形式・公開API・外部サービス・構造大変更 | 停止→選択肢提示→承認待ち |

## 設計原則
1. ロジックと見た目の分離: ルール層=決定論的・エンジン非依存・単体検証可能。表現層はイベント購読のみ、ルールを書き換えない。データフロー: 入力→ルール→イベント→表現。この分離の崩れが中盤以降のバグと冗長化の最大源
2. データ駆動: 数値・定義はコードに埋めない(SO/JSON)。コンテンツ追加=データ追加のみが理想
3. 状態の明示化: 進行は明示的FSM。boolフラグ組合せでの状態表現禁止。可変static/グローバル状態は原則禁止
4. 非決定性の隔離: 乱数・時刻・入力は単一窓口経由(詳細Fable2)
5. 増築と先回りの両方を検知: 同種追加が3回続いたらデータ駆動化/抽象化のシグナル→提案。逆に「将来必要かも」だけの抽象・実装は作らない(YAGNI)

## 実装規律
- 1関心事=1変更単位。無関係なリファクタを混ぜない
- 既存コードは推測せず開いて読む。命名・構造は既存様式に従う
- 編集後diffを読み直し、エッジケースを最低3つトレース
- 不要コードは削除。コメントアウト温存禁止(履歴はgit)
- 完了=検証の証拠を提示した時。未検証なら「実装済み・未検証」と報告

## タスク完了時の定型宣言(毎回・各1行)
```
[F]検証: <実行した確認と結果 | 未検証+理由>
[F]揺らぎ: なし | 検出:<内容>
```
検出時は次タスクへ進まず停止・報告。

## 揺らぎ検知(タスク完了時に走査)
同じ知識(定数・判定・変換)の2箇所以上への重複 / 表現層によるルール状態の直接書換 / 「とりあえず」フラグ・特例分岐の増殖 / 責務を1行で説明できないクラス・ファイル / 過去の設計判断と矛盾する実装(意図的なら判断記録を更新、無自覚なら実装側を修正) / 未使用の先回り抽象

## 新規プロジェクト・大型機能の開始手順
コードより先に確定し判断記録へ: レイヤー構成(ルール/表現/基盤) / データフロー / FSM遷移図 / 非決定性の窓口 / ディレクトリ・命名規約

## セッション運用
HANDOFF.mdが単一の真実。無ければ最小構成(現状 / 判断記録 / 既知問題 / 次の着手点)での作成を提案。開始時に読み、終了時に更新。ゲート未達で次段階へ進まない。通過判定は証拠付き。

## アンチパターン
