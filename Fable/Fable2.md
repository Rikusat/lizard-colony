# Fable2 — コアロジック・データ(Fable0と併読)

読込時宣言: `[F]読込:F2` / 主題: ルール層を決定論的・検証可能・拡張可能に保つ。

## 決定論
- 原則: 同じ入力+同じシード=常に同じ結果。再現テスト・バグ調査・リプレイの全てを支える
- 非決定要素(乱数・時刻・フレーム依存値)は直接呼ばない。シード注入可能な単一窓口経由。エンジン標準乱数/時刻APIのルール層内直接使用をコードベース全域で禁止
- シード固定モードと使用シード表示を早期に仕込む
- **経路統一**: 同じ結果を生む処理はテスト/デバッグ/本番で同一コードを通す。経路別実装・別初期化は「経路で挙動が違う」バグの温床→禁止
- 厳密なリプレイ互換やクロス端末同期が要件の場合のみ浮動小数点のプラットフォーム差を考慮(要件になければ過剰対応しない)

## 状態管理
- 進行は明示的FSM、遷移図を先に書く。遷移はFSM経由のみ、直接書換の抜け道を作らない
- 可変static/シングルトン状態は原則禁止。シングルトンは無状態サービスに限定
- 画面/シーンを跨ぐ残留状態は典型バグ源→生成/破棄のライフサイクルを明示

## データ設計
- スキーマ先行。スキーマは準可逆→決定理由を判断記録へ
- 保存データは不可逆→必ず承認。最初からバージョンフィールド+後方互換を設計に含める
- 派生値は保存しない。保存は原データのみ、派生値は読込時再計算(二重管理=ズレの温床)

## 拡張に耐える設計
- 新要素追加がswitch追記になったらデータ駆動/ポリモーフィズム移行のシグナル(F0増築検知)
- ルール間依存はイベント/インターフェース経由。変更の波及を局所化
- 曖昧な組合せ(効果重複・同時発生・順序依存)は発見時に挙動を定義しテスト化。未定義放置禁止

## 検証可能性
- ルール層はエンジン起動なしでテスト可能な形(純粋クラス/モジュール)を目指す
- 最低限のテスト: 決定論(同一シード=同一結果) / 性質(大量入力で不変条件維持) / 回帰(修正バグごとに再発検知テスト1つ)
- テスト実行コマンドをHANDOFFに記載

## 揺らぎ検知(F0に加えて。コミット前または機能実装3件ごとに走査)
ルール層でのエンジン乱数/時刻API直接呼出(grepで確認) / 判定・計算式の重複 / boolフラグ組合せの状態表現 / テスト経路と本番経路の実装乖離 / 保存データへの派生値・表示用値の混入
