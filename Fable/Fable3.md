# Fable3 — 品質・性能・リリース(Fable0と併読)

読込時宣言: `[F]読込:F3` / 主題: 品質を気合ではなく手順と証拠で担保する。

## バグ修正プロトコル
再現(手順確定)→仮説(候補2-3を確度順)→検証(仮説を1つずつ潰す。いきなり直さない)→修正(根本原因。症状対処なら「暫定」明記)→防御(再発検知テスト/アサーション追加)
- 「経路で挙動が違う」「たまに起きる」の第一容疑者: 非決定要素の初期化経路差と残留状態(F2)
- 修正報告には「再現→修正→再現しない確認」の証拠を添付

## リグレッション防御
- 変更のたびに既存テスト実行を手順化(コマンドをHANDOFF明記)
- 「小さい修正だからテスト不要」禁止。小さい修正ほど事故る
- 不安定テスト(たまに落ちる)を無視・リトライで済ませない。非決定性混入のシグナルとして調査(F2)
- 手動確認項目は通しプレイチェックリストとして文書化、リリース前に証拠付き全消化

## 性能
- **計測なき最適化禁止**。プロファイラで主犯特定後に修正
- ターゲット環境(最低スペック実機/ブラウザ)とフレーム予算を先に決定。開発機で快適は根拠にならない
- 頻出主犯: 毎フレームアロケーション(GC) / 過剰ドローコール / パーティクル・UI毎フレーム更新 / 同期ロード
- 予算内なら可読性優先

## リファクタ
- 機能変更と混ぜない。独立した変更単位で実施
- 大規模リファクタは不可逆寄り→目的・範囲・手順を提示し承認
- 完了条件: 全テストが変更前と同結果。テストなき領域を大きくリファクタしない(先にテスト)

## ビルド・リリース
- ビルド手順(エンジンver・設定・署名・成果物検証)を未来の自分が再現できるレベルで文書化
- リリース間際: 新機能/依存更新/エンジン更新を凍結、diff最小、バージョン番号・パッケージ名・保存互換は全て不可逆扱い(必ず確認)
- リリース版にクラッシュ収集と最小限のプレイ計測を仕込む(個人情報は送らない設計を明記)
- ストア規約・APIレベル等のプラットフォーム要件は記憶で答えず最新公式ドキュメント確認
- 正常系の外側を必ずチェック: 中断/復帰・オフライン・初回起動・旧バージョン保存データでの起動

## 揺らぎ検知(F0に加えて)
証拠なしの「修正済み」報告 / 計測なしの最適化着手 / リファクタと機能追加の混在diff / 修正バグへの再発防止テスト未追加 / ビルド手順が記憶にしか存在しない
