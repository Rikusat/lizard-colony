# trait_system.md — 特性システム設計メモ（レア度撤廃→「皆違って皆良い」）

- 状態: **構想メモ（未実装）**。今後 Fable モデルで設計→実行予定。V5本体とは別スプリント。
- 目的: レアリティの序列を撤廃し、個体の「特性（Trait）」による個性で「皆違って皆良い」を実現する。
- 関連: 純血設計（GameExpansion_V5 Phase 4）・遺伝子ルーレット（roulette.md）・図鑑。

---

## 0. 背景 — レアリティのダブルスタンダード（撤廃理由）

- レアリティシステムの本来の目的は「各個体の獲得体験を追求させる」こと。
- しかし個体の希少性は**個体数**でも決まる。「レア度が高い＝価値が高い」と「個体数が少ない＝価値が高い」が競合＝**ダブルスタンダード**。
- 結果、**レア度5が出ても繁殖で増えると価値が薄れる**。ある程度は諦めのつく設計だが、本アップデートで**レアリティを撤廃**し、"遊び心"＝「皆違って皆良い」を目指す。

## 1. 方針 — 序列（縦）から個性（横）へ

- **表向きのレア度（1〜5の序列）を撤廃。** 個体は「優劣」でなく「どんな特性を持つか」で個性を持つ。
- **ただしレア度は内部数値として残す（内部数値化）。** 表示上の序列は見せないが、特性の希少度・出現率・遺伝難度は内部的に数値管理する。
- 価値の源泉を「引いた運（レア度）」から「育てた過程（掛け合わせの達成）」へ移す。

## 2. 特性（Trait）

- 既存の種族に加え、各個体に**特性**を付与する。特性の例（順次追加）:
  - トライアド / ヴァイブラント / クロノ / ヴォイド / ミミカクシ / アミダグラ /（その他順次追加）
- 各特性に見合った**パーツ・体の装飾・挙動**を追加する（特性が見た目と動きに現れる）。
- 各特性に**内部レア度（数値）**を持たせる（出現率・遺伝難度の管理用・非表示）。
- ※各特性の具体的な意味・見た目・挙動は設計時に確定（命名から世界観を膨らませる余地。Ric承認）。

## 3. 遺伝とやり込み

- **複数のパーツ（特性）を同時に遺伝させるのは膨大な時間・工数がかかる**＝これがやり込み要素のゲーム体験。
- 掛け合わせを重ねて、複数特性を併せ持つ個体を作り上げる過程そのものが価値になる（達成の物語）。
- **ゲーム最終盤に「遺伝を一部固定化するパーツ」を用意予定**（狙った特性を固定して掛け合わせやすくする＝終盤のご褒美・純血設計の「クリア後の種移動アイテム」と同系の"最後の解禁"）。

## 4. 特性カードUI（タップで展開）

- **トカゲをタップすると、その個体の特性カード（簡単な紹介）を展開**できる。
- カードは**特性によって色分け**し、**ロゴを付与**する（特性ごとの視覚的アイデンティティ）。
- カードは「簡単な紹介」＝情報過多にせず、その個体の個性が一目で分かる程度に。

## 5. 設計時に確定すべき事項（Fableモデルでの本格設計時）

- 各特性の意味・見た目パーツ・装飾・挙動・内部レア度・出現率。
- 遺伝ロジック（複数特性の同時遺伝の確率・掛け合わせの仕組み）＝純血設計・ルーレットとの整合。
- 既存セーブへの影響（現在レア度を持つ個体の移行＝レア度撤廃時のデータ変換。資産・個体を壊さない）。
- 特性カードのUI（色分け・ロゴ・展開演出）＝UISkills/fable1準拠。
- 「遺伝固定化パーツ」の解禁条件（終盤）。

## 6. 設計思想（記録）

- 「皆違って皆良い」＝優劣でなく個性。crank.md「遊び心を最重要」の生き物側での実践。
- 価値を「運」から「過程」へ。やり込みの深さが価値を作る（純血設計の「混合は最後のご褒美」と同系）。
- レア度を消すが収集の深さは残す：表向き平等、内部は深い。

# 【本格設計】特性システム 実装設計書（2026-07-22・Claude Opus 4.8 起草／実装は絶対にしない・Ricレビュー用）

> 本節（§7以降）は §0〜6 の構想メモを、**実装可能なレベル**へ拡張した設計書である。**コードは一切変更していない**。各所の **★Ric承認待ち** は、Ricの判断が要る分岐（世界観・レア度撤廃の是非・遺伝の複雑さ・賢者の石の用途）を示す。承認後、§13 の段階に沿って可逆な範囲から実装する。
>
> **コードベース実測（起草時点）で確定した前提**:
> - 個体データ（`Game.makeLizard` / game.js:100）は `{ id, speciesId, morphId, hue, sat, light, pattern, stage, xp, level, injuredT, breedCd }`。**個体にレア度フィールドは無い**。
> - **レア度は派生値**：`speciesById(id).stars`（種族の★1〜5）＋ `morphById(id).mult`（モーフ倍率）から都度計算（game.js:199 等）。fable2「派生値は保存しない」に既に準拠。
> - よって**「レア度撤廃」は保存データの破壊を伴わない**。撤廃＝(a)★の**表示**を止める＋(b)stars/multを**内部数値として残置**（trait_system §1と一致）。
> - 特性は個体への**新規追加フィールド**＝additive。旧個体は「特性なし」で後方互換に動く（allyLv横展開§5tと同じ非破壊パターン）。

## 7. コンセプト整理（純血の上に個性を乗せる）

- 3層で個体を規定する：**種族（species）× モーフ（morph）× 特性（trait）**。
  - 種族＝惑星固有の2種（純血設計・Phase 4）。**不変**。
  - モーフ＝normal/albino/melanistic/golden 等（既存）。**維持**（ただし表向きの序列表現は特性側へ寄せる）。
  - **特性（trait）＝本システムの新規軸**。同じ種×モーフでも特性が違えば「別の個性」。ここに「皆違って皆良い」を宿す。
- **レア度（縦の序列）は表向き撤廃**。★表示・「レア/伝説」ラベルを個性表現（特性）へ置換。stars/multは内部係数として残す（出現率・遺伝難度の管理用・非表示）。
- **価値の源泉を「引いた運」→「掛け合わせた過程」へ**。特性は繁殖の掛け合わせで積み上げる（§9）。

## 8. 個体スキーマの変更案（後方互換・SAVE_VERSION方針）

### 8.1 追加フィールド（additive）
`makeLizard` の返す個体に **`traits` 配列**を追加する（単数 `trait` でなく配列＝§9「複数特性の同時遺伝＝やり込み」を表現するため）。

```
lizard = {
  …既存フィールド…,
  traits: [ { key: "chrono", tier: <内部数値>, /* 発現に必要な最小情報のみ */ } , … ]  // ★追加
}
```

- `key` … 特性ID（`"triad"|"vibrant"|"chrono"|"void"|"mimikakushi"|"amidagura"|…`／§2の命名を軸に、意味・見た目はRic確定）。
- `tier` … その特性の**内部レア度（数値・非表示）**。出現率・遺伝難度の管理用。**表示しない**（§1）。
- **保存するのは原データ（どの特性を持つか）のみ**。特性による**ステータス倍率・見た目パーツは保存せず、`key` から都度解決**（fable2「派生値は保存しない」）。特性定義テーブルは data.js（`TRAITS = {...}`）に置く（データ駆動）。

### 8.2 後方互換と SAVE_VERSION
- **方針A（推奨・非破壊）**: `traits` を**任意フィールド**とし、未定義＝空配列扱い（`lz.traits || []`）。旧個体は「特性なし」で正常動作。**この追加だけならSAVE_VERSION bump不要**（allyLv横展開§5tと同じ）。
- **方針B（スタンプ移行）**: レア度撤廃を「意味づけ」たい場合、既存個体へ**移行時に特性を1つ付与**（例：現在のmorph/starsから初期特性へマッピング）。これは保存内容を書き換えるため **SAVE_VERSION bump ＋ `migrateVnToVn+1` ＋ バックアップ退避（saveBackupKeyVn）＋ 復元ボタン**が必須（Phase4/10と同一手順）。
- **★Ric承認待ち①**：旧個体を「特性なしのまま」にするか（方針A・最小破壊）、「移行で初期特性を付与」するか（方針B・世界観は濃いがセーブ書換＝不可逆）。**推奨は段階：まず方針Aで可逆に導入 → 手応えを見て方針Bを別バンプで**。

## 9. 遺伝ロジック（繁殖で特性がどう伝わるか）

前提：繁殖は既存フロー（トカゲをタップ→相手選択→卵）。遺伝は決定論的窓口（乱数は単一窓口経由・fable2）で処理する。

- **基本継承**：子の `traits` は**両親の traits の和集合を母集団**とし、各特性が独立に確率 `p(trait)` で発現。`p` は特性の内部tier（希少度）に反比例（希少特性ほど伝わりにくい＝やり込み）。
- **複数特性の同時遺伝（§3の核）**：親が複数特性を持つと、子が**全部を継承する確率は各 `p` の積**＝指数的に小さい。これが「膨大な時間・工数のやり込み」を生む（狙った2〜3特性を併せ持つ個体を作る過程が価値）。
- **突然変異**：低確率で親に無い特性が新規発現（既存モーフ突然変異8%と同系の枠。乱数窓口共通）。新規特性の獲得入口の一つ。
- **終盤の遺伝固定化（§3）**：「特定の特性を固定して掛け合わせやすくするパーツ」＝終盤の解禁。狙い特性の `p` を1.0に固定する消費アイテム（純血の「クリア後の種移動」と同系の"最後の解禁"）。**★Ric承認待ち②**：固定化パーツの入手/解禁条件・強さ（やり込みを壊さない範囲）。
- **★Ric承認待ち③（遺伝の複雑さの範囲）**：同時遺伝を「積」で厳しくする度合い、突然変異率、1個体が持てる特性数の上限。**やり込みの深さ ⇔ 理不尽さ**のバランスはRic実機判断。たたき台をCFG化して提示予定。

## 10. 出現・入手経路（★賢者の石を軸に）

特性の入手経路を、既存の獲得ループと整合させる。

- **経路1：繁殖（§9）**＝主経路。既に持つ特性を掛け合わせて濃くする／同時に持たせる。
- **経路2：遺伝子ルーレット（roulette.md）**＝レインボー穴の景品（未所持の新種）に加え、**特性の"種"を出す景品**を検討。純血で「未所持の新種が枯渇した惑星」の、新たな発見の入口（§10 trait_system原文の狙い）。
- **経路3：★賢者の石（four-slit=食/syzygyで貯まる・現状 用途未定）を特性の入手/付与に使う案（本命）**：
  - 案I：**賢者の石を消費して、個体に新規特性を1つ付与/抽選**（レア特性ほど多く要る＝内部tier連動）。→ 純血で種が出揃った後の"深い収集"の資源シンクになり、賢者の石に意味が生まれる。
  - 案II：賢者の石を**§9の遺伝固定化パーツの素材**にする（終盤の狙い撃ち掛け合わせを賢者の石で解禁）。
  - 案III：I+II の併用（付与にも固定化にも使う）。
  - **★Ric承認待ち④（最重要級）**：賢者の石の用途をI/II/IIIのどれにするか。これは「四重スリット＝食」の世界観と、純血後の"やることが枯れない"設計の要。**Ric判断が要る核**。
- **枯渇回避の思想**：純血は「その惑星の固有種2種のみ」で種の収集は早く飽和する。特性は種の上に**横に無限の収集軸**を足す＝惑星に留まる理由と、賢者の石の使い道を同時に供給する。

## 11. 遺伝子ルーレット／純血との整合

- **純血を崩さない（絶対制約）**：特性は**種族を変えない**。特性付与・遺伝はあくまで「同じ固有種の個体の個性」を変えるのみ。惑星の固有種2種の閉じた集合（Phase4）は不変。
- **ルーレットの景品**：レインボー穴＝未所持の新種（種族同一・既存）は不変。特性の種を出すなら**別ポケット/別演出**として足す（既存の確率・#spin-proof幾何・物理は不変＝roulette憲章）。**★Ric承認待ち⑤**：ルーレットに特性景品を足すか、賢者の石経路（§10-3）のみにするか。後者ならルーレット確率・幾何は完全非接触で安全。
- **図鑑との整合**：図鑑は種×モーフ=32エントリ（既存）。特性は**別軸のコレクション表示**（種族図鑑を汚さない別ビュー／「特性コンプ率」）を新設する案。既存32エントリのロジック・報酬は非接触。

## 13. 移行方針・リスク・段階分け【最重要＝破壊的変更の管理】

**本システムは本プロジェクト最大の破壊的変更**（レア度という価値軸の撤廃＝ゲーム経済の根幹）。可逆／不可逆を厳密に分け、可逆から着手する。

### 13.1 可逆／不可逆の切り分け
| 段階 | 内容 | 可逆性 | セーブ |
|---|---|---|---|
| S1 | `TRAITS` データテーブル定義（data.js）＋特性の見た目描画（render.js）＝**表示のみ・付与なし** | 可逆 | 非接触 |
| S2 | 個体に `traits: []` を additive 追加（方針A・未定義=空） | 準可逆 | **非接触**（bump不要・§8.2A） |
| S3 | 特性カードUI・個体詳細の★→特性置換（表示層） | 可逆 | 非接触 |
| S4 | 繁殖の特性遺伝ロジック（§9・決定論窓口）＝**新規個体にのみ付与** | 準可逆 | 非接触（新個体のfield） |
| S5 | 賢者の石/ルーレット経路（§10）＝付与手段 | 準可逆 | 非接触（既存個体のfield更新は追記のみ） |
| S6 | **旧個体スタンプ移行（方針B）** ＝レア度撤廃の意味づけ | **不可逆** | **bump＋migrate＋バックアップ必須** |
| S7 | 遺伝固定化パーツ（終盤解禁） | 準可逆 | 非接触 |

### 13.2 リスクと不可逆性
- **経済の根幹**：レア度撤廃は「売却額・繁殖コスト・図鑑報酬」がstars/multに依存している箇所（game.js:199 等）を**内部残置で温存**すれば数値は不変に保てる。**表示だけ止める**のが安全。★撤廃を「数値も含めて」やるとバランス全崩壊＝別途大調整。**推奨：内部数値は残す（trait_system §1と一致）**。
- **不可逆点はS6のみ**。S1〜S5は全て非破壊で導入でき、手応えを見て止められる。**S6は必ずRic承認＋バックアップ＋復元ボタン＋消失なし（特性は追加のみ＝そもそも個体を消さない）**。
- **確率・物理・純血・魂 不変**：特性は種族を変えず（純血不変）、ルーレット物理/#spin-proofに触れず（案次第で完全非接触）、魂（トカゲ描画の骨格）は特性パーツを**上乗せ**するのみ（既存geometry不変）。

### 13.3 推奨着手順（承認後）
1. **S1（TRAITSデータ＋見た目）を1〜2特性で試作** → Ricが世界観・見た目を確認（可逆・捨てられる）。
2. 承認 → **S2＋S4（additive field＋繁殖遺伝）** で「掛け合わせで個性が伝わる」核を非破壊導入。
3. **S5（賢者の石経路）** ＝★用途承認（§10-4）後。
4. **S3（UI）** を並行。
5. **S6（旧個体移行）** は最後・単独・bump＋承認。

## 14. Ric判断が要る点（一覧・再掲）
- **①旧個体の扱い**：方針A（特性なし据置・非破壊）か 方針B（移行スタンプ・要bump）か。→推奨：Aで導入→後日Bを別バンプ。
- **②遺伝固定化パーツ**：入手/解禁条件・強さ（やり込みを壊さない範囲）。
- **③遺伝の複雑さの範囲**：同時遺伝の厳しさ・突然変異率・1個体の特性数上限。
- **④賢者の石の用途（最重要）**：付与（案I）／固定化素材（案II）／併用（案III）。
- **⑤ルーレット景品に特性を足すか**：足す（要景品設計）／賢者の石経路のみ（ルーレット完全非接触＝安全）。
- **⑥特性のビジュアルアイデンティティ**：色/ロゴの世界観（UISkills追記が要るか）。
- **⑦レア度撤廃の範囲**：表示のみ撤廃・内部数値残置（推奨・非破壊）か、数値も含めた撤廃（要大調整）か。

## 15. テスト方針（実装時・fable2/3準拠）
- **決定論**：同一シード＋同一親＝同一の子traits（遺伝窓口の乱数固定テスト）。
- **性質**：大量繁殖で「同時多特性の出現率が積に一致」「1個体の特性数が上限内」「種族が変わらない＝純血不変」。
- **回帰**：レア度撤廃で売却額/繁殖コスト/図鑑報酬が**変わらない**こと（内部数値残置の証明）。ルーレット確率/#spin-proof不変。既存セーブ（特性なし）が正常load。
- **移行（S6のみ）**：bump前後で個体数不変・通貨/鉱石/設備/味方Lv不変・バックアップ退避・冪等。
