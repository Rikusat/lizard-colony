## 1. 全フェーズ共通の規律（再掲・遵守）

- **聖域**: `slit.js` の物理・確率・生成 / 繁殖の実行ロジック・CD・確率・遺伝 / セーブの単調追加。音のためにルール層へコードを足さない——ルール層に音コードは1行もない状態を維持し、事象は `emit` 経由・音idへの変換は `CFG.soundCues` の単一窓口のみ。
- **音の憲章**: 既定OFF・初回無音。通知を増やさない。系統別音量が実際に効くこと。外部アセット禁止＝WebAudio合成のみ。物差しは SE＝peak / 環境音＝持続RMS・定常性（100ms窓）・低域比率（憲章§3-2の対比表）。惑星差・場所差は**既存の真実から導出する**（SoundSkills.md の原則）。
- **QAゲート**: QA3層 ＋ nodeスイート（本数は実測値で申告） ＋ boot console 0（カナリア先行） → bump-cache → commit → deploy → asset hash照合 → 三者同期clean → 本番実証。同乗内容は全申告。
- **計測の規律**: 代理でなく実物を測る / 検知能力の実証（カナリア）を先に / 実機スクショは非決定的につき比較に使わない / **パスの大小は本番で実際に叩いて確かめる**。実音の確認は自動QAで代替不能——「鳴る経路が存在すること」までを実証し、耳での判定はRicが行う旨を毎回の報告に明記すること。
- **セッション規律**: 20分超過が見えたら中間報告。コンテキスト低下を検知したら成果をコミット＋pushし、記録して停止。重ければフェーズ内で区切って申告してよい。
- 報告は従来様式（[F]検証 / [F]揺らぎ / result）。完了後は指示待ち・自走禁止。

2. **未デプロイなら**、【S2判定=合格】の■デプロイ節をそのまま実施すること:

3. **デプロイ済みなら**、実測結果の報告のみで本フェーズを通過してよい。

## 3. REL-1 (=S3) — 本部 / 巣 / 四重スリットの音

### 3-1 承認済みのたたき台

- **本部** ＝ 低ハム ＋ 起動同期tick（冷たい計器）
- **巣** ＝ 籠もったディレイパッド ＋ 心拍様低音（籠もった安息）
- **四重スリット** ＝ **常時無音 → 全通過の瞬間だけ最重の一撃**（無音が音の一部という設計）

### 3-2 設計要件

- 本部と巣は「場所の環境音」——飼育槽と同じく**疲れないこと・主張しないことが最優先**。数分聴き続けて破綻しない設計であること。
- 三者の質感差が聴いて分かること: **飼育槽＝温かい生命 / 本部＝冷たい計器 / 巣＝籠もった安息**。差が無ければ作り分けの意味がなく、差が大きすぎれば移動のたびに気が散る。
- 場所の切り替わり（飼育槽↔本部↔巣）で音が破綻しないこと。惑星移動の沈み込み方式（1.2秒の無音）が流用できるか判断し、採否と理由を報告すること。
- 【重要】スリットの一撃は「核に予算を集中」の最たるもの。撃破（peak 0.259）を**超える重さを与えてよい**。ただし優先度表「石の生成 ＞ ボス撃破」と整合させること。全通過は極めて稀（設計値1/4339）——その希少性に見合う音であること。プレイヤーが数百回に一度しか聴かない音である。
- 数値ゲート: 環境音2種＝持続RMS・定常性（100ms窓）・低域比率。スリット一撃＝peak（SEの物差し）。ゲート値はCFG化し、閾値を引く前に検知能力の実証（カナリア）を行うこと。
- 場所差の導出も「既存の真実から」を第一候補に検討すること（惑星差を STAGES[].sky から導出したのと同型。本部・巣に固有の既存データが無い場合は、その旨と代替の設計根拠を報告）。
- `?tune=1#sound` で三者（＋スリット一撃の試聴ボタン）を聴き比べられるようにすること。

### 3-3 判定（Ric・実機）

1. 本部・巣を数分鳴らしっぱなしにして疲れないか。
2. 三者の質感差が聴いて読めるか。
3. 場所の切り替わりが不自然でないか。
4. スリットの一撃に「賢者の石が生まれた瞬間」の格があるか。

合格 → デプロイ（同乗全申告・本番実証・三者同期clean） → REL-2へ。

## 4. REL-2 (=S4) — オープニング / Loreムービーの音同期

### 4-1 対象

- オープニング（HOLO BRIEFING）/ Loreホログラムムービー（全章）/ 惑星移動トランジション（音の有無と要否をまず実測し、追加が要るなら提案）。
- 着手前に、対象の正確な一覧（章構成・尺・タイムライン定義の所在）を実測して報告してから設計に入ること。

### 4-2 設計原則

- **音は画のタイムラインに従属する**。同期の真実はムービー側のタイムライン定義ただ一つ——音側に独自の時間表を作らない（二重定義の禁止）。
- **スキップで即無音**。確認を挟まない。残響ごと即断するか短く減衰させるかは提案し、承認を経ること。
- **音OFFで完全に成立すること**。既定OFFのため大半のプレイヤーは無音でムービーを観る。音があることを前提にした演出上の意味付けをしない——無音が基準、音は加点である。
- prefers-reduced-motion 時の扱いを明示すること（静止表示時は音も鳴らさない、が既定の想定。異なる設計にする場合は理由を添えて提案）。
- 【要Ric承認】予算（重さ）の位置づけ: ムービーは稀に観るもの。優先度表のどこに置くか（スリット一撃・撃破との相対）をCCが提案し、Ric承認を経てから実装すること。
- HOLO系の視覚語彙（走査・点灯・fuse）と音の対応は「既存の真実からの導出」を第一候補に検討すること。

### 4-3 判定（Ric・通し）

オープニング →（本編）→ Lore再生 を通しで観て・聴いて判定。スキップ・音OFF・reduced-motion の3経路も確認。合格 → デプロイ → REL-3へ。

## 5. REL-3 — 餌プール・報酬設計の最終調整

**位置づけ**: Ric裁定により、**リリース前の必須ゲート**。音（REL-1・REL-2）の完了後、総仕上げ（REL-4）の前に行う。調整の対象と方向性は**Ricが着手時に指示する**——本節はその受け皿（判断材料の提出と、変更の手順）を定める。

### 5-1 CCの先行提出（判断材料の実測——数値は一切動かさない）

Ricの指示を待たずに準備してよいのは以下の実測のみ:

1. **餌まわりの現況一覧**: 餌の種類と入手経路 / コスト・レート / オート給餌・切れ時トグルの現仕様 / 関連CFGキーの全数と現在値。
2. **報酬の現況一覧**: 報酬の発生源ごと（ルーレット・ミッション・ボス・スリット等、実在するもの全数）に、内容・量・確率・関連CFGキー・決定論/乱数の別。
3. **数値↔テストの対応表**: 各数値に紐づくテスト（黄金値テスト・MC測定・経済系QA等）の一覧——「何を変えるとどのテストが壊れるか」が読める形。
4. **経済フロー図**（テキストで可）: 資源の入口 → 変換 → 出口を一枚に。

### 5-2 調整の手順（1件ずつ・承認制）

- Ricの指示 → CCが影響範囲（テスト・確率・セーブ・既存プレイヤー資産）を先に報告 → 承認 → 実装 → 実測で効果確認 → Ric実機判定。
- 【重要】確率・期待値に触れる変更は、該当ルールの**MC再測**を伴うこと（ルーレット系は roulette_rules.md §4 の型）。**黄金値テストが壊れる変更**は、壊れる理由と再基準化の手順を先に報告すること。
- 既存プレイヤーの資産に**損失感ゼロ**——減る方向の変更は、払い戻し・経過措置の設計を添えて提案すること。セーブは単調追加の原則を維持。
- 全変更はCFG経由。CCは推測で数値を動かさない（従来規律）。

### 5-3 [A]手触り詰めとの関係（旧裁定の範囲改定）

- 旧版§5-2の裁定「[A]未調整でも公開を止めない」は範囲を改める: **餌プール・報酬設計はリリースゲート（本フェーズで完了必須）**。それ以外の[A]（意匠色・モーション値・命名語感等）は従来どおり非ブロッキング——Ricが触りたい項目があれば本フェーズに同乗させてよい。
- CCは[A]対象キーの一覧と検分ページを最新化し、Ricの調整を支援すること（5-1の先行提出に含めてよい）。

### 5-4 完了判定

- **Ricが「バランス確定」と宣言した時点で完了**。確定値をCFGとHANDOFFに記録 → デプロイ → REL-4へ。
